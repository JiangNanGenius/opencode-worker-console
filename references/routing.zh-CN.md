# 路由与套餐利用率

[English](routing.md)

优先分配完整任务、利用可用套餐，同时满足模型能力和上下文需求。订阅套餐已经支付，DeepSeek
直连余额属于增量支出。模型选择遵循以下四档规则。进入 Ultra 时通过检查点新建原生模型会话，不重放已完成工作。

## 四档与 Kimi 额度保护

| 档位 | 当前模型 | 使用定位 |
| --- | --- | --- |
| Fast | DeepSeek Flash | 方向明确、模型延迟影响具体交付的任务 |
| Normal | K2.8 Preview / Qwen3.8 Flash | 日常调查、实现、测试的默认档 |
| Deep | Qwen3.8 Max | 需要较强推理的复杂工作 |
| Ultra | Kimi K3.1 Pro（标准版、max） | 极复杂架构、疑难根因、长程推理与低效任务升级 |

原厂旧 K3 和 Ark K3 已从新任务路由与选项中移除，历史记录保留真实模型。协调者在明确困难时直接选 Ultra；
普通任务连续两轮无实质进展后，先复核检查点，再决定升级。认证、权限及环境故障先解决阻碍。
问题明确后的常规实施交给 Normal。`ultra_fallback_to_deep` 默认开启：Ultra 确认额度、五小时／月度用量或余额耗尽后，可续接 Qwen3.8 Max。
保持 Ultra 档位、任务 ID、会话、授权与检查点，不再向 Max 以下降级；两者均不可用时等待。
额度有新鲜恢复证据后，只在属于当前任务回合的空闲检查点回到 K3.1 Pro；已完成报告不重跑。
认证、权限、网络故障、禁用模型和人工排除不算额度耗尽。显式指定 profile 或设置 `capability_floor=ultra`
时，仍等待所需模型。设置 `ultra_fallback_to_deep=false` 可关闭此默认接力。

进入 Ultra 保留任务 ID、授权与检查点，新建模型会话，传递已完成工作、证据、决策和剩余目标；不重放已完成操作。
Kimi 默认基础／最高周保护为 30%，达到或低于当前有效保护线的额度仅供 K3.1 Pro 使用。
动态释放开关 `kimi_weekly_reserve_dynamic` 默认开启：前半周保持基础值，后半周闲时按
`应急线 + (基础值 - 应急线) × clamp(距周刷新秒数 / (7天 / 2), 0, 1)` 降低保护，
其中应急线为基础值与 5% 中的较小值。基础为 30% 时，距刷新 84 小时为 30%、42 小时为 17.5%、
24 小时约 12.14%、周期末为 5%。按真实周刷新时刻判断，不按星期几。
Ultra 正在排队或执行，或原生 K3.1 Pro 在近 30 分钟有活动时，暂停释放并恢复基础保护；
周额度、刷新时间或需求信号未知／过期时同样保持基础值，周额度未知时仍阻止普通 Kimi 派发。
关闭开关则固定使用基础保护。账户卡按后端读数显示基础、当前有效保护、已释放百分点、暂停原因和下次周刷新。
已释放百分点只是保护线的降低幅度，不代表当前可用余额，也不能收回已消耗额度。
周额度、五小时额度和账户总额度分别判断；
不以四倍周额度估算总池。缺失或过期读数显示未知，官方明确没有周窗的套餐显示不适用。
账户总池必须来自实际账户查询并核对推理密钥归属；账户登录成功不代表总额度已取得。
这是调度预留，已发请求与上游计量延迟可能造成短暂越界。周剩余 ≤5% 且预计撑不到刷新时，Ultra 并发为 1。

## 通用路由模式

Worker Desk 不要求特定供应商，也不要求用户同时购买多个套餐。先建立 profiles，再在
**模型与路由**中选择：

- **每档单模型**：只用基础 `routing`，分别为Fast、Normal、Deep 和 Ultra 任务选择一个 profile。
- **主模型 + 备用**：把模型放进前后两个独立阶段；前一阶段全部不可用时才进入下一阶段。
- **固定比例池**：把两个或更多 profile 放在同一阶段，使用整数权重，比例不会自动改变。
- **额度自适应池**：为阶段显式开启有边界的连续曲线。双供应商阶段支持比例控制点
  （`ladder`）；两个或更多供应商的阶段支持通用 `curve`：每个供应商的基准权重乘以
  `min(1, 续航) ** strength`。续航刚好达标时为中性，续航为零的池权重归零，额度未知或
  过期的池保留其配置基准，而不会抹掉其他池已知的压力。按量余额不携带时间窗，因此永不
  与订阅续航直接比较。

每个任务档位可以独立混合顺序回退和加权分配。只有一个套餐时完全不需要策略；一个套餐加一个
按量备用时，配置两个单模型阶段即可。Ultra 配置策略仍只放具有 Ultra 能力的模型（本机为 K3.1 Pro）。
不要把 Max 加入 Ultra 的主阶段或备用阶段；桥接层从 Deep 路由提取合格的 Qwen3.8 Max，且仅在确认 Ultra 耗尽后放行。

任务档位按未解决的不确定性和模型更快完成工作的预期收益选择，不按工作量大小或模型强弱排序。Normal 是
普通可执行工作的默认档：目标、主要约束和验收明确的实现、调查、测试、文档、打包、迁移和部署，
即使需要读取大型仓库、修改很多文件、运行很久，也仍用 Normal；仅方向明确或不确定性低，本身不构成
选择或切换到 Fast 的理由。Fast 是有能力的低时延优先档：方向、约束和验收明确，且有合理、有
证据支撑的预期——模型更快完成能实质推进一个具体的近期验收/交付里程碑（明确紧迫的交付/截止
时间，或协调方识别、当前确已就绪且正被本工作阻塞的依赖任务或环节）时使用；它可以完整承担功能、
已知修复、测试、文档修改和常规部署，也可以自行查明普通局部细节，不需要逐行规定方法，也不要求
提前读完整仓库。Deep 处理复杂推理，Ultra 处理极复杂架构、疑难根因和长程推理，
或在连续两轮无实质进展并复核检查点后升级。上下文大、任务体量大和重要本身不构成 Deep 条件，紧迫本身也不能绕过未解决
的推理需求；真正需要 Deep 的任务不设额外总量限制。

档位衡量的是 Worker 仍需消除多少不确定性以及模型更快完成工作的预期收益，不代表模型智力或结果质量高低。
Fast 与 Normal 都应完整、正确地交付。普通可执行工作（方向、约束和验收明确的实现、测试、文档、
部署和收尾）默认 Normal；有明确紧迫性/截止时间，或协调方识别的真正瓶颈节点——剩余模型工作正是
当前有影响的阻塞点——且方向、约束、验收明确时用 Fast；需要定义目标或规则、调和模糊冲突的要求、
设计新的系统结构、寻找未知的系统级
根因，或处理特别复杂的逻辑时才使用 Deep。任务名称本身不决定档位：按明确清单移动文档是 Normal，
从混杂资料中判断保留、合并和删除也是 Normal；方向、约束和验收明确、直接阻塞一个已就绪下一步
构建的已知补丁可以用 Fast，而为未来版本准备组件、其他前置条件仍在推进时一般用 Normal。

Fast 的实用门槛是：派发前已经明确结果、方向或主要约束和可观察的完成证据，且有合理、有
证据支撑的预期——模型更快完成能实质推进一个具体的近期里程碑：当前确已就绪且正被本工作阻塞的
依赖任务或阶段，或明确紧迫的交付/截止时间。常规的顺序依赖（下游最终需要这份产出）本身不构成
Fast 理由，仅拥有关键资源也不等于能证明提速收益；不要把每个常规流水线阶段都称为关键并整条
链切到 Fast。排队或资源争用、编译、外部 CI/测试执行和单纯等待不会被更快的模型产出加速：除非
剩余模型工作本身就是当前有影响的阻塞点，否则保持 Normal。前期规划即使很困难，方向确定后的完整实现
默认仍是 Normal；只有存在具体时延收益时才切到 Fast，Deep 不确定性消除后回到 Normal。执行过程
本身仍需开放式调查或解决多个重要且互相关联的选择时使用 Normal。不要仅为换档重启已经有效工作的
任务并重复发送上下文。

额度不参与协调模型的档位选择。协调模型只按未解决的不确定性和模型更快完成工作的预期收益选择 Fast、Normal
或 Deep（默认 Normal），并保持 `profile=auto`；桥接层随后独立执行额度与供应商策略。自动路由任务的
`status`/`wait`/`collect` 投影同样遵循该边界：只要仍有合法自动路由，就省略所选模型、路由历史、容量等待
原因、单个供应商/档位/套餐耗尽及恢复提示；仅请求档位被阻塞而其他档位仍有可用路由，或读数未知/未证实
时，保持普通排队任务且不返回恢复对象，`wait` 继续等待；基础任务仍保留请求档位与能力下限。只有全部档位的
所有已配置自动路由都被证实额度耗尽时，才给出一个
通用 `automatic_routes_exhausted` 阻塞。未知/过期读数、认证/传输错误、人工排除、能力下限以及被禁用或未配置的
策略都不会升级为该消息。显式 profile、能力下限以及认证、权限、传输错误保留可操作细节；控制台与
`quota` 视图保留完整运维遥测。`delegate-opencode quota
--tier-guidance --compact` 只返回这份稳定约定，完整 `quota --tier-guidance` 仅供运维排障。
续航信号以实测工作消耗速度为主：用窗口剩余额度百分比除以拟合出的活跃
消耗速率，得到剩余可用工时，再与距窗口重置的实际时间比较。旧的“剩余额度比例 ÷ 距刷新所剩
时间比例”只在尚无消耗样本时作为冷启动先验——例如剩 20% 且窗口也只剩 20% 时间时为 `1.0x`，
并不紧张；剩 20% 但还有 40% 时间时为 `0.5x`。空闲时段不计入工作速率，避免含大量空闲的样本
低估消耗。同一供应商内部取最紧张的窗口作为其瓶颈；跨套餐供应商的降载压力则取各供应商有效
瓶颈续航的**最大值**，前提是所有已配置套餐都有可靠读数；否则合并压力记为未知，而非零。这与控台中描述性的合并
工作池拟合是两套口径。近期有效补额最多可把护栏阈值放松 30%；而完整的“补额安全”旁路是更严格
的独立条件：补额在两小时内到达，且每个当前可用供应商按各自实测消耗预测都能独立撑到该补额，
绝不把多个并行续航相加。
若 Fast 与 Normal 共用同一个紧张套餐，且没有续航更健康的 Normal 套餐，桥接层可把更多方向明确
的工作放到 Fast 路由。若方舟紧张但 Kimi 仍健康，则保留 Normal 路由去消费 Kimi，不能因为方舟
余额低反而把更多请求推到只使用方舟的 Fast。运维诊断中的 `quota_posture` 只汇总这项内部决策；
协调模型不读取它，也不改变请求档位。

可选的 `quota_spillover` 规则补上了“套餐健康”和“套餐完全耗尽”之间的空档。一级把后段按量
Profile 逐步混入 Fast 或 Normal 的第一阶段；二级使用更快的独立渐进曲线，并把自动 Normal
的来源暂时换成第一个可用的 Fast 来源池。Deep 和显式指定 Profile 永不改变。Agent Plan 预设的
一级/二级基准为 38%/25%，一级上限为 33%；DeepSeek 实时人民币余额不低于 30 元时，二级高压
上限为 100%。闲时在整个二级阶段都可使用该上限；峰时从 33% 起步，仅在来源套餐续航进入极端
紧张区间时连续升到 100%。这些数值是动态护栏而非固定切换点：合并工作池按实测工作消耗
拟合，并对在派任务量做有界需求修正；近期有效补额最多可把两级阈值放松 30%，而完整的
“补额安全”旁路另有更严格条件：补额须在两小时内到达，且每个当前可用供应商都能独立撑到。
可靠低压样本会立即触发保护；恢复则采用 5 个百分点退出余量加 5 分钟迟滞，短暂好转不会立即退出保护。迟滞只对可靠信号生效：未知数据会抑制新的降载动作，但不保证维持原级别。
额度未知时不虚构补额。北京时间工作日仅
09:00-12:00、14:00-18:00 为高峰，周末（包括调休上班日）始终按闲时处理；工作日法定节假日由
可配置订阅识别并缓存在本机。订阅或余额状态不确定时使用较低上限。

当普通档一个套餐健康、另一个套餐低于一级续航阈值时，分流按紧张套餐自身计算，不再被合并池
掩盖。DeepSeek 只替代紧张套餐原有份额，并沿同一条续航曲线连续变化；极端压力下可替代该份额的
全部，但不会侵占健康套餐的份额。同能力的 Normal 和 Deep 组合会先把紧张套餐的份额交给健康
套餐伙伴，可真正到达 100% / 0%，不保留装饰性的 1%。DeepSeek 主要承接 Fast 这类只有单一
套餐来源的阶段，或两个套餐共同紧张时的总体缺口；二级极端压力下可到 100%。随着紧张套餐刷新
时间临近，同一剩余额度的续航比会升高，该套餐逐步回归，DeepSeek 连续退到 0。

套餐双模型曲线和兜底替代曲线共同组成一个控制器：Kimi 与方舟先按各自刷新时间和真实续航分配
套餐工作，DeepSeek 再只替代当前紧张的一侧。因此三个余额会共同影响同一次决策，但不会被压成
一个误导性的统一百分比，也没有突然切换供应商的硬门槛。

控台总工作池会把按量余额增加识别为新的观测周期，不会再用充值后的余额减去充值前的样本。
当余额实测消耗和官网 Token 计价都可用时，采用其中较高的消耗速度约束续航，避免某个包含大量
空闲时间的信号把预计时长拉长。路由降载仍只看订阅套餐续航，不把按量余额计入降载判断。

额度引导与供应商无关。“模型与路由”可为每个已配置服务商选择：可用时读取实时额度、手动填写
滚动窗口（剩余比例、窗口时长、带明确时区的刷新时间）、为按量账户设置金额低余额阈值、忽略，
或标记为 `prepaid`。没有余额接口时还可手动填写当前余额。可配置的 Fast 临界续航阈值同时作用于
实时与手动窗口；金额模式使用该服务商自己的低余额阈值。信号未知时保持正常路由，不会假装额度
充足或耗尽。

`prepaid` 表示可补充的预付额度（例如阿里云 Token Plan 坐席组），不是必须撑到续费日的限时配额。
它沿用现有服务商记录，无需新增顶层配置：

```json
{"budget_signals": {"bailian-token-plan": {"mode": "prepaid"}}}
```

真实可用的 Credits 仍是硬性准入来源，确认的零额度、过期和推理凭据熔断仍会拦截。按续费日计算的
“是否会在刷新前耗尽”不再触发降载、权重衰减、主动降档、Max→Flash 替换，也不会因其他套餐紧张而
把该预付服务的份额溢出。其控制续航为中性（`1.0`、服务商等级 `0`），其他套餐继续保护自己的额度；
全局降载也不会替换仍有可用预付额度的 Normal 阶段。控制台保留实时 Credits、实测续航和真实续费
时间，但不会仅因续费日较远就把可充值的额度标成即将耗尽。

预付额度的恢复以当前推理 Key 为准。全账户 Credits 聚合读数可能包含另一个坐席，因此永不自动清除
已确认的当前 Key 耗尽或拒绝状态。替换推理 Key 会改变其不透明文件身份并解除旧熔断；当前 Key 上
已验证的完成响应或显式 `quota --retry-provider` 也可恢复。轮换独立用于查询额度的 AK/SK 从不等于
推理 Key 恢复；控制面查询失败只是未知遥测，不是推理 Key 失败。

### 手动额度快照

没有余额接口的订阅（例如阿里云 Token Plan Credits）可以导入控制台快照，而不是伪造实时遥测：

```sh
delegate-opencode quota --import-snapshot /private/path/snapshot.json
```

快照包含供应商、套餐额度与剩余量、重置时间、采集时间、可选来源说明和可选新鲜度时长（分钟）。
界面会明确标注新鲜度，绝不把它当作实时读数。重置时间已过、或导入时已超过新鲜度期限的正数读数
只是历史记录：它不能解除已记录的耗尽状态或计费熔断。只有更新的、仍处于当前周期内的正数读数、
经过验证的模型成功回复，或显式手动重试才能证明恢复。乱序导入会被拒绝，完全相同的重复导入是幂等
空操作。阿里云 Max 与 Flash 共用同一 Credits 快照；每个套餐池保留各自独立的信号。

## 能力下限（可选）

Deep 的实际能力下限始终至少为 Deep，历史任务同样适用；省略字段或填写较低下限都不能让 Deep 降到 Flash。
Ultra 的默认最低能力为 Deep，仅允许经过耗尽验证后续接 Qwen3.8 Max；显式 Ultra 能力底线会关闭这一例外，额度压力不能覆盖底线。

任务规格可设置 `capability_floor`（`fast`/`normal`/`deep`/`ultra`），并必须附带非空的
`capability_reason`（1-500 字符）。能力下限不得高于所请求档位；`normal` 下限只允许
Normal/Deep/Ultra 第一阶段中的 profile，`deep` 下限只允许 Deep/Ultra 第一阶段，`ultra` 下限只允许 Ultra 第一阶段中确有 Ultra 能力的模型；把已知较弱模型放入该阶段不能满足底线。兜底、降载和同会话改路
都不会选择低于下限的 profile；若均不可用，任务以 `capability_floor_unavailable` 排队等待而
不是降级。父任务续接自动继承该下限。这用于刻意要求“不得降级”的场景（例如无论额度压力如何，
较轻路由都无法保证正确性的任务），不是常规升档手段；普通任务省略这两个字段。

```json
{
  "routing_policy": {
    "background": [
      [{"profile": "plan-a", "weight": 2}, {"profile": "plan-b", "weight": 1}],
      [{"profile": "backup", "weight": 1}]
    ]
  },
  "routing_dynamics": {
    "background": {
      "0": {"ladder": [[3, 1], [2, 1], [1, 1]]}
    }
  }
}
```

额度自适应必须按阶段主动开启。普通固定池即使刚好使用 `1:1` 或 `2:1`，也不会被系统暗中改变。

## AFP-equivalent

Worker Desk 把成本假设和真实额度分开保存，默认值可在控台修改：

```text
1 AFP-equivalent = ¥0.002
¥1 = 500 AFP-equivalent
Kimi ¥699 = 349,500 AFP-equivalent（仅表示购买成本的名义等价值）
```

这不代表 Kimi 官方提供 349,500 AFP，也不能凭它推算固定 Token 额度。若一个完整 Kimi 账期实际
处理 `M` 百万 Token，`349500 / M` 只能得到该账期的混合名义成本；没有分模型明细或多组不同配比
样本，就不能分别反推出不同模型。

成本估算按当前启用模型和实际观测的 Token 计算，不用已退役模型的固定配比推算。
官方返回的实时用量为实际依据；控制台将实际值、估算值和名义成本分别显示。
