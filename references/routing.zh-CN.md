# 路由与套餐利用率

[English](routing.md)

优先分配完整任务、利用可用套餐，同时满足模型能力和上下文需求。订阅套餐已经支付，DeepSeek
直连余额属于增量支出。不要为了换渠道拆碎任务，也不要重复发送整个上下文。

## 通用路由模式

Worker Desk 不要求特定供应商，也不要求用户同时购买多个套餐。先建立 profiles，再在
**模型与路由**中选择：

- **每档单模型**：只用基础 `routing`，分别为快速、普通、深度任务选择一个 profile。
- **主模型 + 备用**：把模型放进前后两个独立阶段；前一阶段全部不可用时才进入下一阶段。
- **固定比例池**：把两个或更多 profile 放在同一阶段，使用整数权重，比例不会自动改变。
- **额度自适应池**：为双供应商阶段显式开启有边界的连续曲线。所填比例是控制点，保存的权重是中性基准；新鲜额度续航在控制点之间连续插值，额度未知或过期时保持基准。

每个任务档位可以独立混合顺序回退和加权分配。只有一个套餐时完全不需要策略；一个套餐加一个
按量备用时，配置两个单模型阶段即可。下面的 Ark/Kimi 方案只是可选示例，不是平台默认要求。

任务档位按推理性质选择，不按工作量大小或模型强弱排序。Fast 可以完整承担路径和验收明确的
功能、已知修复、测试、文档修改和常规部署。Normal 是明确目标需要更广调查或综合判断时的强能力
默认档，即使需要读取大型仓库、修改很多文件、运行很久，或完整承担实现、测试、文档、打包和部署，
也仍可使用 Normal。
Deep 用于抽象或尚不明确的目标、未定位的系统级根因、架构取舍，以及具有特别困难约束的复杂逻辑。
上下文大和任务重要本身不构成 Deep 条件；真正需要 Deep 的任务不设额外总量限制。

档位衡量的是 Worker 仍需消除多少不确定性，不代表模型智力或结果质量高低。Fast 与 Normal 都应
完整、正确地交付。方向、主要约束和验收已明确时优先 Fast；不要求逐行指定方法，Worker 仍可调查
局部细节并选择常规实现。方向明确但执行中仍需开放式调查、综合大量证据或处理多个互相关联的判断
时使用 Normal；需要定义目标或规则、调和模糊
冲突的要求、设计新的系统结构、寻找未知的系统级根因，或处理特别复杂的逻辑时才使用 Deep。
任务名称本身不决定档位：按明确清单移动文档是 Fast，从混杂资料中判断保留、合并和删除则是
Normal。

Fast 的实用门槛是：派发前已经明确结果、方向或主要约束，以及能够证明完成的可观察证据。
前期规划即使很困难，方向确定后的完整实现仍可使用 Fast，即使任务很大、跨文件或运行很久。
只有执行过程本身仍需开放式调查或解决多个重要且互相关联的选择时才使用 Normal。不要仅为换档
重启已经有效工作的任务并重复发送上下文。

额度只能在 Fast 与 Normal 都能完整胜任时作为决胜条件，不能改变能力要求。每组连续派发前读取
一次 `delegate-opencode quota --tier-guidance`。续航系数等于“剩余额度比例 ÷ 距刷新所剩时间比例”：
剩 20% 且窗口也只剩 20% 时间时为 `1.0x`，并不紧张；剩 20% 但还有 40% 时间时为 `0.5x`，才是
明显超前消耗。若 Fast 与 Normal 共用同一个紧张套餐，且没有续航更健康的 Normal 套餐，方向明确
的任务应更多选择 Fast。若方舟紧张但 Kimi 仍健康，则保留可用 Normal 的任务去消费 Kimi，不能
因为方舟余额低反而把更多请求推到只使用方舟的 Fast。桥接层返回 `quota_posture` 标签：
`fast_preferred` 表示同等胜任时偏 Fast，`normal_flexible` 表示 Normal 独占套餐健康、两档都可按需
选择，`neutral` 表示额度没有倾向。当前 Kimi 路由最低档就是 Normal；在 `normal_flexible` 下应结合
错误与返工风险、紧急程度和任务大小判断，Normal 可以放心使用，但不是强制选择。

可选的 `quota_spillover` 规则补上了“套餐健康”和“套餐完全耗尽”之间的空档。一级把后段按量
Profile 逐步混入 Fast 或 Normal 的第一阶段；二级使用更快的独立渐进曲线，并把自动 Normal
的来源暂时换成第一个可用的 Fast 来源池。Deep 和显式指定 Profile 永不改变。Agent Plan 预设的
一级/二级基准为 38%/25%，一级和 DeepSeek 高峰上限为 33%；DeepSeek 闲时且实时人民币余额不低于
30 元时，二级上限提高到 50%。这些数值是动态护栏：工作池按近期真实消耗拟合，若下一次补额很近
且能显著恢复总池，两级生效阈值最多自动下调 30%；额度未知时不虚构补额。北京时间工作日仅
09:00-12:00、14:00-18:00 为高峰，周末（包括调休上班日）始终按闲时处理；工作日法定节假日由
可配置订阅识别并缓存在本机。订阅或余额状态不确定时使用较低上限。

额度引导与供应商无关。“模型与路由”可为每个已配置服务商选择：可用时读取实时额度、手动填写
滚动窗口（剩余比例、窗口时长、带明确时区的刷新时间）、为按量账户设置金额低余额阈值，或忽略。
没有余额接口时还可手动填写当前余额。可配置的 Fast 临界续航阈值同时作用于实时与手动窗口；
金额模式使用该服务商自己的低余额阈值。信号未知时保持正常路由，不会假装额度充足或耗尽。

```json
{
  "routing_policy": {
    "background": [
      [{"profile": "plan-a", "weight": 2}, {"profile": "plan-b", "weight": 1}],
      [{"profile": "backup", "weight": 1}]
    ]
  },
  "routing_dynamics": {
    "background": {
      "0": {"ladder": [[3, 1], [2, 1], [1, 1]]}
    }
  }
}
```

额度自适应必须按阶段主动开启。普通固定池即使刚好使用 `1:1` 或 `2:1`，也不会被系统暗中改变。

## 方舟 Agent Plan

通过 OpenCode 的私有凭据存储连接 `volcengine-agent-plan`。Key 不进入任务、仓库、命令参数或
报告。启用对应 Profile 后，Worker Desk 自动提供 Responses API 配置：

| Profile 示例 | 模型 | 上下文 / 最大输出 | 思考强度 |
| --- | --- | --- | --- |
| `ark-auto` | `volcengine-agent-plan/ark-code-latest` | 客户端上限 1,024,000 / 32,000 | `max` |
| `ark-evolving` | `volcengine-agent-plan/doubao-seed-evolving` | 1,024,000 / 65,536 | `max` |
| `ark-k3` | `volcengine-agent-plan/kimi-k3` | 1,024,000 / 65,536 | `max` |
| 仅手动选择 | `volcengine-agent-plan/deepseek-v4.1-flash` | 1,024,000 / 65,536 | `max` |

SDK 为 `@ai-sdk/openai`，套餐 Base URL 为
`https://ark.cn-beijing.volces.com/api/plan/v3`。推理 Key 仍由 OpenCode 私有存储，生成的运行
配置不含 Key。`ark-code-latest` 跟随方舟控制台选择，模型身份不够确定；需要明确能力时使用
固定 Evolving 或 K3。1,024,000 客户端上限用于避免 OpenCode 在 256K 提前压缩，实际后端限制
仍以当次模型为准。

AFP 查询使用另一组火山控制面 AK/SK。按[凭据说明](credentials.md)注册两个元数据引用后，
Worker Desk 在进程内签名固定的 `GetAFPUsage` 与 `GetPersonalPlan` 请求，只返回套餐和窗口信息。
未配置时仅显示额度未知，不影响推理。四个额度窗口和所有方舟模型共用同一 AFP 续航信号。

来源：[OpenCode 接入](https://www.volcengine.com/docs/82379/2373741)、
[套餐概览](https://www.volcengine.com/docs/82379/2366394)、
[GetAFPUsage](https://www.volcengine.com/docs/82379/2479847)、
[GetPersonalPlan](https://www.volcengine.com/docs/82379/2546382)。

## 可选 Ark/Kimi 套餐优先预设

全新安装使用 `--preset ark-agent-plan` 会建立：

- 快速任务：Ark Auto → DeepSeek 直连。
- 普通任务：原厂 Kimi K2.8 : 方舟 Seed Evolving = 1:1 → Ark Auto → DeepSeek。
- 深度任务：原厂 Kimi K3 : 方舟 K3 = 2:1 → 普通任务组合 → Ark Auto → DeepSeek。

调度器只使用第一个存在可用模型的阶段。协调 Agent 只提交任务层级并保持 `profile=auto`；显式
Profile 只用于用户指定模型或受控对比。比例统计的是实际
派发任务数，不是 Token 或花费；等待会话并发、文件锁或额度恢复不会消耗轮次。

该预设还默认启用 Kimi 周额度 5% 低位保护，并提供 1 个全局原厂 K3 槽位。达到或低于阈值后，
自动 Normal 任务排除 Kimi；自动 Deep 任务最多运行一个原厂 K3，其余选择方舟 K3 或后续阶段。
桥接层优先读取有效的 `overall` 汇总，否则读取精确七天窗口，绝不会拿 5 小时窗口代替周额度。
阈值和 K3 槽位数都能在“模型与路由”中修改。

自动路由跳过至少一个前置阶段并进入配置的 `fallback` 时，任务状态会返回
`fallback_used: true` 和路由说明。普通模型选择保持静默，只有实际启用最终兜底时才通知用户。

Kimi 是经济性基准，因为同一个 Kimi 模型经方舟 AFP 购买通常更贵。每个任务池都有自己的连续、
带重置时间的负载曲线：

| 组合 | 基准 | 允许范围 |
| --- | --- | --- |
| 原厂 Kimi K3 : 方舟 K3 | 2:1 | 从 3:1 经 2:1 连续变化到 1:1；方舟 K3 不会超过原厂 |
| 原厂 Kimi K2.8 : 方舟 Evolving | 1:1 | 从 2:1 经 1:1 连续变化到 1:2 |

每个窗口的续航信号为“剩余额度比例 / 距离重置的剩余时间比例”，取最紧张窗口。数据过期、缺失或
未认证时保持基准。两侧续航相差 2 倍时会得到中间比例，相差 4 倍时才到达外侧边界。Fast、一级
降载和二级降载分别使用自己的曲线；二级降载借用含多个供应商的 Fast 池时，也继承 Fast 的曲线。
Ark Auto、Evolving 和 K3 共用一个信号，因此 Auto 多用会自动压低后续方舟
占比。接口明确为零时移除该渠道。确认的额度/窗口终止或模型端 HTTP 429 可以直接在同一个
OpenCode 会话中切换下一路由；桥接层保留完整对话与工作区，排除失败供应商，并要求新模型检查
已有工作，不重复已经完成的编辑或外部副作用。

额度降载生效时，还可为自动路由的 Fast/Normal 长任务启用同会话换模型续接。达到设置时长后，
桥接层只排入一次下一模型消息，等待当前模型回合自然结束，不主动中断；Deep 与显式指定 Profile
不参与。任务 ID、工作区和完整对话保持不变，路由历史记录 `queued_boundary_switch`，新模型先检查
已有工作再继续。桥接层内部的普通换模不打扰协调 Agent，只在路由历史中保留排障记录；只有最终
兜底或无法继续才显式返回。控台可为降载级别变化、供应商耗尽/恢复及这些模型切换发送 Bark
推送；推送只报告状态，不参与路由决策。

## AFP-equivalent

Worker Desk 把成本假设和真实额度分开保存，默认值可在控台修改：

```text
1 AFP-equivalent = ¥0.002
¥1 = 500 AFP-equivalent
Kimi ¥699 = 349,500 AFP-equivalent（仅表示购买成本的名义等价值）
```

这不代表 Kimi 官方提供 349,500 AFP，也不能凭它推算固定 Token 额度。若一个完整 Kimi 账期实际
处理 `M` 百万 Token，`349500 / M` 只能得到该账期的混合名义成本；没有分模型明细或多组不同配比
样本，就不能分别反推出 K3 与 K2.8。

按可配置假设 Auto=50、Evolving=250、方舟 K3=1000 AFP/百万 Token，以及 K3 2:1、第二档 1:1：

```text
Ark AFP = 333.33D + 125N + 50S
```

`D/N/S` 是深度、普通、小任务的百万 Token 数。动态比例下为
`1000*rD*D + 250*rN*N + 50*S`，其中 `rD` 在 1/4 到 1/2 之间连续变化，`rN` 在
1/3 到 2/3 之间连续变化。系数和活动会变化；方舟接口返回的实时 `Used` 才是实际依据，控台会把实际值、
估算值和名义人民币成本分开显示。
